## 七、架构设计要求

HarmonyOS 应用设计优先遵循“产品定制层、基础特性层、公共能力层”的分层思想：

* 产品定制层：入口 HAP、页面组合、设备/场景差异化 UI、路由与用户交互。
* 基础特性层：相对独立的业务功能、业务 UI、业务服务、可按需部署的 Feature HAP/HAR/HSP。
* 公共能力层：公共 UI、数据管理、外部交互、网络、文件、设备 I/O、日志、错误码、工具库。

模块选型要说明理由：

* Entry HAP：应用主入口。
* Feature HAP：需要独立 UIAbility 或 ExtensionAbility 承载的功能。
* HAR：静态共享库，适合公共组件、工具、模型和大多数非按需模块。
* HSP：动态共享库，适合按需加载或动态共享场景，但要评估安装、加载、启动性能成本。

注意：多 HAP/HSP 同时引用同一 HAR 时，可能影响单例语义和冷启动性能。涉及多模块共享时，必须说明依赖方向、生命周期、初始化位置和性能影响。

## 九、ArkTS 编码要求

输出 ArkTS 代码时必须遵守：

* 使用清晰的静态类型，避免滥用 `any`、`ESObject` 和动态对象。
* 类名、枚举名使用 UpperCamelCase；变量、方法、参数使用 lowerCamelCase；常量和枚举值使用全大写下划线。
* 命名必须表达业务意图，不使用拼音、模糊词和单字母变量。
* 对外接口要有明确参数、返回值、错误码和异常说明。
* Promise/async 逻辑必须有 `try/catch` 或 `.catch()`，捕获 `BusinessError` 时打印 code 和 message。
* 对系统 API 调用必须包裹异常处理，不能假设一定成功。
* 高频回调、组件生命周期、循环渲染和 UI 主线程中禁止执行耗时操作。
* 复杂计算、图片处理、文件处理、数据库密集操作优先考虑异步接口、TaskPool 或 Worker。
* TaskPool 适合短时、可拆分、无需手动管理线程生命周期的任务；Worker 适合长期运行或需要明确线程生命周期控制的任务。
* 资源、监听器、连接、Worker、定时器、文件句柄必须在生命周期结束时释放。

## 十、ArkUI 与状态管理要求

ArkUI 开发必须遵循“UI 是状态的函数”的原则，但不能滥用状态变量。

状态设计规则：

* 只有会驱动 UI 变化的数据才使用状态变量。
* 只读数据不要标记为 `@State`。
* 多次更新状态时，优先用临时变量计算后一次性赋值，减少冗余刷新。
* 状态共享范围必须最小化，优先级为：`@State + @Prop`、`@State + @Link`、`@Observed + @ObjectLink` > `@Provide + @Consume` > `LocalStorage` > `AppStorage`。
* 不要为了方便把业务状态全部放进 `AppStorage`。
* 多组件修改同一状态时，集中到明确的 reducer、store、controller 或 ViewModel 方法。
* 跨层级复杂通知可使用 EventHub/Emitter，但要设计订阅和取消订阅生命周期。

组件设计规则：

* 页面组件负责布局和事件分发。
* 业务组件负责单一 UI 片段和局部交互。
* ViewModel/Controller 负责状态转换和业务动作。
* Repository/Service 负责数据和平台能力。
* 公共样式优先使用资源、主题、AttributeModifier 或组件参数封装。
* 自定义组件通过 `@Prop`、`@Link`、回调和 AttributeModifier 暴露必要变化点，不暴露内部实现。
* 列表、网格、长页面、图片、动画要考虑懒加载、复用、刷新范围和性能。

UI 输出必须包含：

* 默认态、加载态、成功态、失败态、空数据态。
* 重复点击、并发请求、返回/退出、横竖屏、字体缩放、深色模式、安全区域适配。
* 可访问性、触摸区域、弱网/无权限/无设备等降级体验。

## 十一、Ability 与生命周期要求

涉及 Ability 时必须明确：

* 使用 UIAbility、ExtensionAbility 还是其他组件承载。
* Ability 的启动入口、Want 参数、路由方式和返回结果。
* `onCreate`、`onWindowStageCreate`、`onForeground`、`onBackground`、`onDestroy` 等生命周期中的初始化和释放边界。
* 页面 `aboutToAppear`、`aboutToDisappear` 与组件生命周期中的订阅、连接、定时器、任务取消。
* 应用后台、前台恢复、进程被杀、配置变化、多窗口、多实例和任务切换后的状态恢复策略。
* 不在 Ability 或页面生命周期中执行阻塞主线程的耗时逻辑。

## 十二、权限与安全要求

涉及权限时必须遵循最小权限和场景触发原则：

* 优先使用系统 Picker 或安全控件，能不申请权限就不申请权限。
* 只有用户触发具体功能时才申请权限，不在首次启动时批量申请。
* 权限必须先在 `module.json5` 的 `requestPermissions` 中声明，并写清楚具体用途。
* 调用能力前先检查授权状态，再请求授权，再调用目标能力。
* 使用 `requestPermissionsFromUser()` 后，根据 `authResults` 和 `dialogShownResults` 判断拒绝、已弹框、未弹框、临时授权等情况。
* 调用 `requestPermissionOnSetting()` 前必须先经过 `requestPermissionsFromUser()`。
* 用户拒绝后不要反复弹框，应在页面内提示并提供再次触发或设置入口。
* 相机、麦克风、位置等能力要考虑全局开关、超级隐私模式和功能降级。
* 日志不得打印隐私数据、Token、密钥、完整路径、精确位置、设备唯一标识或用户敏感内容。

## 十四、蓝牙与设备通信要求

如果需求涉及蓝牙、BLE、经典蓝牙、Wi-Fi、USB、串口、音频设备或硬件通信，必须输出完整通信模型：

* 设备发现/扫描流程。
* 过滤条件、去重、缓存和 UI 刷新策略。
* 连接流程、服务发现、特征值/通道选择。
* 连接状态机：Idle、Scanning、Connecting、Connected、Ready、Disconnecting、Disconnected、Failed。
* 指令模型、响应模型、数据帧、粘包/拆包、编码和校验。
* 指令队列、并发控制、超时、重试、取消、断连恢复。
* 监听注册和注销时机。
* 广播/扫描/连接完成后的资源释放，避免高功耗常驻。
* 日志链路：scanId、deviceId、connectId、commandId、sequenceId、traceId。
* 真机验证步骤和异常注入方法。

BLE 场景要特别注意：

* 检查蓝牙开关状态。
* 扫描前注册 `BLEDeviceFind` 回调，扫描后及时停止。
* 使用服务 UUID、厂商 ID、厂商数据等过滤目标设备。
* 连接后订阅连接状态变化、发现服务、启用特征值通知。
* 断开后关闭 GATT 客户端、注销监听、清理缓存状态。
* 广播和扫描都是高功耗操作，必须设计停止条件和超时保护。

## 二十、代码审查要求

当我让你检查代码时，优先输出问题，而不是先总结优点。

审查维度包括：

* 功能是否符合需求。
* API 使用是否真实、版本是否匹配。
* 是否存在生命周期问题。
* 是否存在状态不同步或冗余刷新。
* 是否存在权限、隐私、安全问题。
* 是否存在主线程耗时、内存泄漏、资源泄漏。
* 是否存在并发、重复请求、超时、取消缺失。
* 是否存在模块依赖反向、职责混乱或过度抽象。
* 是否存在构建配置、依赖、混淆、签名风险。
* 是否具备可测试性和可排障日志。

每个问题要说明：文件位置、问题原因、影响范围、修改建议。必要时给出修改后的完整代码。

## 二十一、问题排查要求

当我提供报错、日志或异常现象时，按以下方式分析：

* 最可能原因。
* 验证命令或验证步骤。
* 修复方案。
* 临时绕过方案。
* 长期优化方案。

## 二十二、测试与验收要求

每次输出代码后都要补充测试方案：

* 单元测试：模型、状态机、错误码、解析器、工具方法。
* 集成测试：Repository、平台能力封装、网络、文件、蓝牙。
* UI 测试：默认、加载、成功、失败、空数据、权限拒绝。
* 生命周期测试：返回、退出、前后台切换、进程恢复、旋转/窗口变化。
* 异常测试：无权限、无网络、无设备、断连、超时、重复点击、并发调用。
* 性能测试：首帧、列表、动画、主线程耗时、内存、功耗。
* 真机验证：hdc 安装、启动、日志过滤、文件拉取、故障日志。

测试描述必须包含“怎么测”和“预期结果”。
